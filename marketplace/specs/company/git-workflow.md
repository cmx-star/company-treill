# 公司 Git 工作流

涉及创建或切换分支、提交、合并、Tag、推送、Hotfix、发版或 Git 流程审查时，必须读取并应用本规范。先检查仓库规则和实际分支，绝不推断已经获得改变 Git 状态的授权。

先判断当前仓库适用哪种模型，再执行 Git 操作。项目已有明确分支或发布规则时，以更具体且可验证的项目规则为准；发现冲突时先说明，不混用两套流程。

## 入口检查

1. 读取当前项目 AGENTS.md、发布文档、CI、Hook、当前分支和工作区状态。
2. 区分只读检查与会改变状态的操作。创建或切换分支、提交、合并、打 Tag、推送和发布必须在用户授权范围内。
3. 默认使用 dev/prod-* 模型。只有项目规则、CI、发布文档及当前、默认或活跃分支确认仓库实际使用 master/dev/release 时，才切换到老项目模型；不能根据 Vue 版本或其他技术栈推断。
4. 操作前检查 diff，保留他人和本地已有改动，不夹带无关文件。
5. 未经授权，不暂存、清理、还原、覆盖或移动用户已有改动。

## 当前分支模型

| 分支 | 用途 |
| --- | --- |
| dev | 总开发分支 |
| dev-<version> | 版本开发分支 |
| dev-<username> | 开发人员分支 |
| dev-<username>-<feature> | 开发人员功能分支 |
| dev-<username>-<project> | 开发人员项目分支 |
| dev-<username>-<version> | 开发人员版本分支 |
| prod-<version> | 对应版本的生产分支 |
| hotfix-prod-<version>-<username> | 生产版本紧急修复分支 |

## 老项目分支模型

仅在检查仓库后确认它实际使用 master/dev/release 时采用以下模型。只看到孤立或长期未使用的同名分支，不足以覆盖当前默认流程。

| 分支 | 用途 |
| --- | --- |
| master | 稳定生产分支，只合入已自测并通过 QA 或项目既定验收的 release 代码；上线从此分支构建并按项目规则打 Tag |
| dev | 开发主分支；小项目可按项目权限直接提交，多人协作从此创建 feature-* 分支并在完成后合回 |
| release | 测试分支，只接收 dev 合入；项目没有独立测试阶段时可以省略 |
| hotfix-* | 从 master 创建的线上紧急修复分支；验证后合回 master 和 dev |

使用老项目模型时，不直接在 master 或 release 开发。发版 Tag 沿用仓库已有命名；没有既有约定时，可采用 tag-<version>，例如 tag-1.0.0。

## 创建或切换分支

1. 检查工作区状态、当前分支、远端和目标基线。
2. 从项目证据确认分支模型和命名规则。
3. 确认目标分支不存在命名冲突。
4. 存在未提交改动时，判断切换是否会覆盖或混入这些改动。
5. 只有用户授权创建或切换分支后才执行。
6. 不擅自 stash、清理或还原工作区。

## 日常开发与提交

- 个人开发分支至少每日形成一次内容明确、可恢复的提交；提交数量不能替代自测和质量。
- 需要远端备份时，按项目推送策略执行，不从“需要备份”推断已获推送授权。
- 经常把 dev 合入个人开发分支，避免长期脱离主开发线；个人分支自测通过后再合入 dev。
- 提交前检查 status、diff 和暂存区，只提交当前任务相关内容。
- 格式化变化必须与任务相关，不能覆盖或丢失他人代码。
- 删除代码前确认调用方、替代方案和兼容影响。
- 使用项目已有的 Prettier、ESLint、lint-staged、commitlint 和 Git Hook。
- 普通错误或警告应从代码或配置根因修复。

### 提交步骤

1. 确认当前分支符合项目流程。
2. 运行与改动范围和风险匹配的检查。
3. 检查工作区和暂存区，不夹带无关文件。
4. 检查是否包含密钥、构建产物、个人配置或敏感路径。
5. 使用项目已有提交格式；没有约定时使用准确、简洁的工程描述。
6. 只有用户授权提交后才执行 git commit。
7. 提交后报告 commit SHA、提交内容和仍未执行的推送或合并动作。

## 检查例外

- ESLint 和 Prettier 本身不属于淘汰项。
- 全局变量应在项目 ESLint 配置中按实际来源声明。
- 只有规则误报、生成代码或无法立即迁移的受控旧代码等明确场景，才使用最小范围的 eslint-disable，并写明原因。
- 能够包围单行或代码块时，不禁用整文件。
- git commit --no-verify 不是日常方案。
- 只有真实生产事故、项目流程允许、无法在时限内修复检查且用户明确授权时，才能跳过 Hook。
- 跳过检查时记录原因、风险和后续补跑动作。
- Prettier 与 ESLint 冲突时，先简化代码或修正配置，不靠大范围禁用掩盖冲突。

## 合并和推送

执行前确认：

- 源分支和目标分支。
- 合并方式和冲突处理原则。
- CI、测试和发布条件。
- 远端名称和目标分支。
- 是否需要删除分支。
- 回滚方式。

合并、推送、强制推送、删除分支和创建 PR 是独立动作。普通 git push、force push 和删除远端分支不得共享一个模糊授权。

禁止使用会丢失工作区内容的破坏性命令，除非用户明确要求并已经说明影响。

## 默认模型的 Hotfix 与发版

1. 禁止直接向旧生产分支提交修复。
2. 基于旧 prod-<version> 创建本次发版使用的新 prod-<new-version>，版本号必须按项目事实确认。
3. 基于新生产分支创建 hotfix-prod-<new-version>-<username>。
4. 修复并自测后合回新生产分支；后续本次发版修改继续进入新生产分支，不合回旧生产分支。
5. 将新生产分支发布到预生产环境，由开发和测试验证。
6. 预生产验证通过后，通知产品经理、项目经理和测试等相关人员，再发布生产环境。
7. 生产发布后由开发和测试再次验证，并及时更新发版记录或 Tag。
8. 将新生产分支回合并到 dev，避免修复在后续版本丢失。

## 老项目模型的 Hotfix 与发版

1. 从 master 创建 hotfix-*，不要直接向 master 提交修复。
2. 修复并按项目既定方式验证后，把 Hotfix 合回 master。
3. 从 master 构建并按项目规则打 Tag。
4. 同一修复合回 dev。
5. 项目保留长期 release 分支时，再按其发布规则同步。

## 发布授权边界

以下动作分别确认：

- 版本号修改。
- 变更日志。
- 发布分支和合并。
- Tag。
- 推送。
- 制品构建。
- 预生产部署。
- 生产部署。
- 发布后验证。
- 回合并。

不要把“批准发布”自动扩展为强制推送、删除分支、跳过检查或修改生产数据。

## 交付记录

说明：

- 实际使用的分支模型和证据。
- 执行的 Git 操作。
- 当前分支、commit 和远端状态。
- 检查结果和跳过项。
- 合并目标和冲突处理。
- Tag、制品、部署和发布状态。
- Hotfix 回合并状态。
- 仍需人工完成或批准的动作。

不要把未提交、未推送、未部署或未验证的状态描述为完成。
