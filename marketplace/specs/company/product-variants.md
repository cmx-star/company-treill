# 公司前端产品版本兼容

前端改动可能因私有部署、公有云、中性品牌、海外市场、外部服务可用性、本地化或版本能力而变化时，必须读取并应用本规范。通用 Vue 编码问题不属于本规范范围。

把产品版本标签转换成可验证的能力差异，避免版本判断散落在组件、页面和服务调用中。

## 建立版本事实

1. 从项目类型、配置、构建脚本、产品文档或现有调用链确认版本来源。
2. 不得从文件名、域名、标签名称或技术栈猜测版本行为。
3. 将以下内容先视为候选维度，而不是既定 API：
   - 部署形态：私有部署、公有云、离线或混合部署。
   - 品牌形态：公司品牌、中性品牌或客户定制品牌。
   - 市场区域：国内、外贸、海外或指定区域。
   - 外部服务：是否允许联网、服务是否可用、是否需要替代实现。
   - 本地化：语言、时区、日期、货币、地址和法规。
   - 版本能力：功能开关、授权、兼容版本和迁移要求。
4. 确认这些维度能否组合、互斥关系、默认组合和仍受支持的组合。
5. 证据不足时记录未知，不创建推测性的枚举、环境变量、组件 props 或支持承诺。
6. 只列出本次变更影响的能力，例如品牌展示、外部资源、云端服务、语言格式或合规内容。

## 选择实现边界

- 在应用配置或适配层集中完成“版本组合 -> 能力”的映射。
- 让公共组件消费语义明确的 props、主题令牌、文案资源或项目已有上下文。
- 不让叶子组件直接读取部署版本、租户信息或构建环境。
- 品牌差异优先落到主题、图标和文案资源。
- 市场差异优先落到 i18n、区域格式、链接和合规内容。
- 部署差异优先落到服务可用性与外部资源能力。
- 业务页面差异留在业务层，构建差异留在构建或部署层。
- 只有差异属于稳定的公共组件契约时才增加组件 API。
- 新能力默认采用可选、可回退的增量契约。
- 修改既有默认值、删除字段或改变事件语义时，必须说明兼容影响和迁移路径。

## 实施步骤

1. 写出受影响组合、预期行为、失败或降级行为，以及不受影响组合。
2. 定位项目中现有版本识别入口和能力判断方式。
3. 区分共享逻辑、配置差异和确实需要独立实现的行为。
4. 优先复用现有能力模型，不在组件或业务代码中散落环境判断。
5. 公共契约变化时，先取得批准并给出兼容和回退路径。
6. 为每个受影响组合验证正常路径、失败路径和默认回退。

## 专项检查

### 私有部署

- 是否意外依赖公网资源、遥测、CDN 或云端服务。
- 外部服务不可用时是否有明确降级。
- 内部地址、客户标识和部署信息是否暴露到前端。

### 中性品牌

- 是否仍显示公司名称、Logo、域名、帮助链接或版权信息。
- 主题、图标和文案是否来自已有品牌能力，而不是条件字符串。

### 海外或外贸市场

- 是否硬编码中文。
- 是否假设国内时区、日期、货币、地址或电话格式。
- 链接、地图、支付、统计、客服和合规内容是否适用于目标市场。
- 本地化缺失时的回退语言是否符合项目规则。

### 版本能力

- 默认版本和缺失配置时的行为是否明确。
- 功能开关和授权是否在正确边界消费。
- 旧版本是否需要迁移、兼容分支或降级提示。

## 禁止做法

- 不在多个组件中重复添加 isPrivate、isCloud、isNeutral、isOverseas 等相互组合的布尔开关。
- 不为每个版本复制一套公共组件。
- 不把版本差异藏在无业务含义的 CSS 类名、魔法字符串或散落环境变量判断中。
- 不以删除功能代替版本隔离，除非需求明确要求。
- 不把某个客户的临时差异提升为公司公共规则。
- 不重复通用 Vue、Git、检查或提交流程；使用项目规则和对应 Skill。

## 完成标准

- 每个受影响组合都有明确行为和验证证据。
- 默认版本、失败降级和回退行为清晰。
- 共享代码没有引入隐式品牌、区域或部署耦合。
- 公共契约和迁移影响已经说明。
- 已验证组合、未运行组合和缺少产品定义的组合明确区分。
- 未验证的产品版本不外推为已支持。
